# Ingredient Master 적재 규칙

## 목적

이 문서는 `전국통합식품영양성분정보_원재료성식품_표준데이터` CSV 또는 Parquet에서 서비스가 사용할
Ingredient Master를 만드는 방법을 설명한다.

Ingredient Master는 신선식품 도메인의 **재료(Ingredient) 축**만 관리한다. 상품이나 원천 데이터의
한 행을 그대로 저장하지 않으며, 여러 상품·레시피·향후 영양 정보가 함께 가리킬 수 있는 **조리 전
재료 또는 중간 재료 단위**를 저장한다. 양념육·훈제육·밀키트·완제품 같은 푸드 상품과 메뉴·상황 같은
요리 의도는 이 Master의 identity가 아니다.

현재 MVP의 물리 저장소 이름은 호환성을 위해 `food_master.food`와 `food_id`를 유지한다. 이 문서에서
말하는 Ingredient는 해당 물리 레코드가 표현하는 논리적 대상이다.

```text
원천 식품 데이터
   │
   ├─ 식품 identity 선택
   ├─ 이름·코드 충돌 해소
   └─ 필요한 하위 식품만 추가
   │
   ▼
food_source 1행 + ingredient 레코드 여러 행
```

## Ingredient로 만드는 기준

### 1. 대표식품은 기본 Ingredient다

대표식품은 기본적으로 하나의 Ingredient가 된다.

```text
대표식품코드 = 02001
대표식품명   = 감자
중분류        = 수미 / 대지 / …

→ Ingredient = 감자
→ basis_level = REPRESENTATIVE
```

감자의 품종, 생것·삶은것 같은 조리 상태, 원산지, 생산월, 영양성분은 감자라는 identity를 바꾸지
않는다. 이런 값은 `food`에 넣지 않으며, 나중에 원천 관측 데이터로 연결한다.

### 2. 하위 분류는 실제로 다른 식품일 때만 추가한다

중분류라고 해서 모두 Ingredient가 되는 것은 아니다. 아래 두 경우에만 별도 Ingredient를 만든다.

#### 독립 식품

중분류 자체가 구매·조리·검색에서 구별되는 재료일 때다. 대표식품을 parent로 둔다.

```text
호박 → 애호박
파   → 대파
토마토 → 방울토마토
```

예를 들어 `애호박` Ingredient의 parent는 `호박`이며, basis는 원천 중분류 `0619805`다.

#### 결합 식품

대표식품명과 중분류명을 함께 써야 실제 식품명이 되는 경우다. 이때도 대표식품을 parent로 둔다.

```text
전분 + 고구마 → 고구마 전분
당면 + 고구마 → 고구마 당면
```

Ingredient Master에는 소면·우동·대파·애호박·방울토마토 같은 독립 재료와 감자 전분·고구마 전분·
옥수수 전분·고구마 당면 같은 결합 재료가 포함되어 있다.

### 3. 크기 차이는 Ingredient를 늘리지 않는다

`기름가자미(20cm미만)`, `기름가자미(25-29cm)`처럼 크기만 다른 원천 중분류는 `기름가자미` 한
Ingredient로 묶는다. 크기 값은 Ingredient identity가 아니라 향후 관측 또는 속성으로 연결할 값이다.

같은 방식으로 갈치의 크기 구간은 `갈치`, 보구치의 크기 구간은 `보구치` 하나로 만든다. 어떤 원천
중분류 코드들이 하나의 Ingredient에 포함되는지는 Ingredient 생성 근거로 보존한다.

냉장·냉동, 포장 단위, 소비기한은 Ingredient identity가 아니라 상품·물류 속성이다. 생것·삶은것 같은
원천 관측 상태도 원천 observation으로 남긴다. 다만 상품이 양념·조리·제품화되어 최종 섭취를 목적으로
하면 Ingredient가 아니라 푸드 상품으로 분류한다.

## 코드와 이름이 충돌할 때

공식 대표식품 코드 하나가 서로 다른 재료 이름을 가리키는 경우가 있다. 이때 코드만으로 Ingredient를
식별하면 서로 다른 식품을 잘못 합칠 수 있다.

`source_identity_key`는 이 문제를 해결하는 안정적인 원천 식별자다.

```text
K-FIND:{대분류코드}:{해결된 대표식품코드}:{공백을 제거한 해결된 이름}
```

예를 들어 원천 코드 `06101`은 다음 두 Ingredient를 만든다.

| 원천 코드 | 원천 이름 | 저장하는 basis code | source_identity_key |
| --- | --- | --- | --- |
| `06101` | 상추 | `06101-01` | `K-FIND:06:06101-01:상추` |
| `06101` | 생강 | `06101-02` | `K-FIND:06:06101-02:생강` |

반대로 같은 식품의 표기 차이는 하나로 합친다.

```text
맵쌀 국수 + 멥쌀 국수
→ Ingredient = 멥쌀 국수
→ source_identity_key = K-FIND:01:01010:멥쌀국수
```

충돌·표기 병합 규칙이 없는 원천 코드는 자동으로 Ingredient를 만들지 않고 검토 대상으로 남긴다.

## 데이터 품질 원칙

- 원천 코드 충돌은 이름만 보고 임의로 합치지 않는다.
- 판매명에 Ingredient 이름이 없으면, 검토된 동의어 또는 명시적인 상품 카테고리 근거가 있을 때만 연결한다.
- 상품의 손질·절단·크기·품종·원산지·냉장/냉동은 Ingredient를 새로 만들지 않고 상품과 Ingredient의 관계에 남긴다.
- 한 상품 안에 여러 재료가 섞였거나 재료/푸드 경계가 불명확하면 하나의 Ingredient로 억지로 연결하지 않고 보류한다.
